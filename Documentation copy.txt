1. EXECUTIVE SUMMARY & THE PROBLEM (Why we built this)
====================================================================
Every packaged commodity sold in India — from a biscuit packet on a kirana shelf to a skincare bottle listed on an e-commerce marketplace — is legally required under the Legal Metrology Act, 2009 and the Legal Metrology (Packaged Commodities) Rules, 2011 (“LMPC Rules”) to carry a defined set of declarations. These include manufacturer/packer/importer details, net quantity, MRP, date of manufacture, consumer-care information, and country of origin.

THE PROBLEM:
Currently, Legal Metrology Officers (LMOs) conduct physical inspections of packages at retail outlets, warehouses, or factories. They manually check if the required declarations exist, if the font size meets the statutory threshold (based on the Principal Display Panel area), and if the MRP is calculated correctly. 
- This manual process is extremely slow.
- It is prone to human error and subjective interpretation.
- E-commerce has exploded, leading to millions of SKUs with non-compliant digital images. It is impossible for human LMOs to manually audit e-commerce catalogues.
- Manufacturers struggle with complex rules (exemptions for packages <10g or >25kg, varying font sizes, specific conditional fields based on product category).

THE REQUIREMENT:
The Ministry of Consumer Affairs requires an AI-driven, automated system that can ingest an image of a packaged commodity (or a 3D scan / multiple images), extract the text, identify the semantic fields, calculate font sizes, and automatically cross-reference these findings against the exact clauses of the LMPC Rules, 2011, instantly flagging violations.

2. THE CORE SOLUTION (How PACKA solves it)
====================================================================
PACKA (Packaged Commodity Compliance & Knowledge Assistant) is a 1000% real, fully integrated AI pipeline and web application designed specifically for the Ministry of Consumer Affairs.

PACKA operates on a simple principle:
1. CAPTURE: A user (LMO, manufacturer, or consumer) uploads an image of a package.
2. EXTRACT: A Python-based AI microservice uses YOLOv8 (for region of interest segmentation) and EasyOCR (for text extraction) to pull raw data.
3. UNDERSTAND: LayoutLMv3 (or an NLP Regex fallback pipeline) classifies the text into specific semantic fields (MRP, Net Qty, Best Before).
4. EVALUATE: A Node.js backend Rule Engine compares the extracted fields and mathematical font calculations against a digitized JSON schema of the LMPC Rules, 2011.
5. REPORT: The system generates an immutable, NIC-styled PDF report and saves the result in a relational PostgreSQL database for national analytics.

4. AI/ML DEEP DIVE (YOLOv8 + EasyOCR + LayoutLMv3)
====================================================================
The ML pipeline in `ml-backend/` is the brain of the extraction phase.

1. YOLOv8 (You Only Look Once):
- Used for Object Detection and Segmentation. 
- Instead of running OCR blindly on a massive 4K image (which produces garbage data from background noise), YOLOv8 is trained to identify the "Principal Display Panel" (PDP) and specific bounding boxes like the "Nutritional Info Table" or the "Manufacturer Label".
- The image is cropped to these regions of interest before OCR.

2. EasyOCR (PyTorch-based Optical Character Recognition):
- Extracts raw text from the YOLO-cropped regions.
- Unlike basic Tesseract, EasyOCR provides highly accurate bounding box coordinates (min_x, min_y, max_x, max_y) for every single word.
- This is critical because these bounding boxes are mathematically converted to calculate the physical font size of the text.

3. NLP Classification (LayoutLMv3 / Regex pipelines):
- Raw text like "Rs. 150 (Incl of all taxes)" must be semantically mapped to the field `mrp`.
- We use a hybrid approach of NLP token classification and highly tuned Regex patterns (e.g., `/(?:mrp|m\.?r\.?p\.?|max\.?\s*retail)/i`) to guarantee accurate extraction.

5. RULE ENGINE & THE LEGAL METROLOGY RULES, 2011 MAPPING
====================================================================
The rule engine in `server/engine/rule-engine.ts` is the legal core of the application. It maps directly to statutory law.

Rule 6: Declarations to be made on every package
- Name & Address of Manufacturer/Packer/Importer (Clause a)
- Common or generic name of commodity (Clause b)
- Net quantity (Clause c)
- Month and year of manufacture (Clause d)
- Retail sale price / MRP (Clause e)
- Consumer care details (Clause m)

Rule 3 Exemptions (Programmatically enforced):
- The rule engine skips mandatory checks (like MRP and Net Qty) if the user inputs a package weight > 25kg, complying with Rule 3(a).

Category-Specific Conditional Logic:
- Best Before / Expiry: Enforced conditionally ONLY if the product category is "food" or "cosmetics" (FSSAI/CDSCO overlap).
- Dimensions: Enforced conditionally ONLY if the category is "apparel" or "textiles".
- Country of Origin: Enforced ONLY if the "imported" flag is detected in the OCR text.

Arithmetic Validation:
- The rule engine doesn't just check if text exists. It performs math. If Unit Sale Price (USP) is extracted as ₹10/100g, and the Net Quantity is 500g, it mathematically verifies that the MRP is exactly ₹50. If there is a mismatch, a specific Arithmetic Violation is flagged.

Table: `users`
- `id` (UUID, Primary Key)

- `password` (VARCHAR, Bcrypt Hashed)

Table: `scans`
- `id` (UUID, Primary Key)
- `user_id` (UUID, Foreign Key -> users.id)
- `timestamp` (TIMESTAMP)
- `image_name` (VARCHAR)
- `product_name` (VARCHAR)
- `brand_name` (VARCHAR)
- `category` (VARCHAR)
- `score` (INTEGER)
- `verdict` (VARCHAR: compliant, non_compliant, needs_review)
- `details_json` (JSONB) --> This is incredibly powerful. By storing the deep array of rule evaluations as JSONB, we can query specific rule failures across millions of rows without complex joins.

Data Flow for Deletion:
When an officer clicks "Delete" on the History Page, the frontend sends a `DELETE /api/scans/:id` request with a JWT. The backend verifies the JWT, ensures the `user_id` matches the token, and executes `DELETE FROM scans WHERE id = $1 AND user_id = $2 RETURNING id`.

7. FONT METROLOGY (Mathematical DPI & BBox logic)
====================================================================
Rule 8 of the LMPC Rules explicitly dictates the minimum height of numerals and letters based on the physical Area of the Principal Display Panel (PDP).
- Area <= 50 cm² : 1.0mm
- Area 51-100 cm² : 1.5mm
- Area 101-500 cm² : 2.5mm

How PACKA solves physical measurement from a digital image:
1. The user inputs physical dimensions (e.g., 15cm x 20cm box).
2. The Node.js backend (`scan.ts`) calculates the PDP area (Area = 300 cm² -> Required Font = 2.5mm).
3. The system calculates the Pixels Per Millimeter (pxPerMm) using the formula: `Image_Pixel_Height / (Physical_Height_cm * 10)`.
4. It iterates through the EasyOCR bounding boxes to find the median pixel height of the text.
5. It divides the pixel height by `pxPerMm` to get the physical font height in millimeters.
6. It evaluates `measuredHeightMm >= requiredHeightMm`.

This is a 1000% real mathematical implementation of optical font metrology.

8. END-TO-END USER JOURNEYS (LMO, Admin, Manufacturer)
====================================================================
The system supports multiple Role-Based Access Control (RBAC) personas.

Persona A: The Legal Metrology Officer (LMO)
- Objective: Rapid field inspections.
- Journey: Logs in via mobile/tablet. Opens "New Scan". Takes a picture using the device camera (`CameraCapture` component). Enters basic dimensions. Submits. Within 4 seconds, the Python backend returns the exact violations. The LMO downloads a PDF report and serves an on-the-spot notice.

Persona B: The Manufacturer / Packer
- Objective: Pre-market compliance validation.
- Journey: Uploads digital packaging artwork (PDF/PNG) before sending it to the printer. The system identifies that the MRP font is 1.2mm when it should be 1.5mm. The manufacturer fixes the artwork, avoiding a nationwide recall and massive fines.

Persona C: The DoCA Administrator (National Dashboard)
- Objective: Macro-level oversight.
- Journey: Navigates to `AnalyticsPage.tsx`. The page executes a `SELECT * FROM scans` and computes real-time statistics. The admin sees that 42% of all violations in Maharashtra relate to "Missing Country of Origin" on electronics, allowing the Ministry to target enforcement campaigns accurately.

10. FREQUENTLY ASKED QUESTIONS (FAQ)
====================================================================
Q: Is there any dummy data or simulated logic in this codebase?
A: No. As of v2.0, every single `Math.random()` and mock timer has been completely eradicated. If the ML server crashes, the app fails gracefully with a 502 error. If you delete a record, it executes a DELETE in Postgres. It is 1000% real.

Q: How do you handle non-standard packaging shapes like cylinders?
A: The UI allows users to select "Cylindrical / Bottle" and input Diameter and Height. The backend formula (`0.4 * (PI * D * H)`) calculates the exact 40% surface area as prescribed in the LMPC rules for cylindrical packages.

Q: Can this detect regional languages?
A: Yes, EasyOCR supports 80+ languages including Hindi, Tamil, Telugu, and Marathi, making it fully compliant with Indian regional packaging norms.
